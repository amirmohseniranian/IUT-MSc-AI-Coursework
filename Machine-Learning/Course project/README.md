# Gaussian Process Regression for Esfahan Weather

## Abstract

This project implements an end-to-end Gaussian Process Regression (GPR) pipeline for daily weather variables in Esfahan, Iran. It retrieves hourly weather data from the Open-Meteo Historical Weather API, validates and aggregates the observations into a daily dataset, fits an independent Gaussian-process model for each target, evaluates the models with a chronological 80/20 hold-out split, and exports predictions, uncertainty estimates, metrics, figures, metadata, an audit report, and a reproducible submission package.

The central modeling assumption is a fixed periodic structure. Each scalar target is modeled with a Gaussian process using an `ExpSineSquared` kernel with a fixed period of 365.25 days and a `WhiteKernel` noise component. Wind direction is treated as circular rather than linear: daily directions are aggregated with circular statistics, and the model learns the sine and cosine responses separately before reconstructing the predicted angle.

This repository is best understood as a reproducible scientific software pipeline rather than a benchmark study. The source contains the implementation and the machinery for generating results, but it does not include a fixed set of numerical experiment outputs. Accordingly, this README does not report performance values that have not been generated by an executed run.

## Scientific Background

### Problem formulation

Let \(x_t\) denote the daily time coordinate, represented in the implementation by `day_index`, and let \(y_t^{(j)}\) denote the \(j\)-th weather target on day \(t\).

For the scalar targets, the implementation fits separate Gaussian-process regressors:

$$
f_j(x) \sim \mathcal{GP}\left(m_j(x), k_j(x,x')\right),
$$

The observations are modeled through a noisy likelihood.

The implementation uses `normalize_y=True`, so scikit-learn normalizes each scalar response internally before fitting and transforms the predictions back to the original target scale.

### Periodic covariance model

The core covariance function is the `ExpSineSquared` kernel:

$$
k_{\mathrm{per}}(x,x')
=
\exp\left(
-\frac{2\sin^2\left(\pi d(x,x')/p\right)}{\ell^2}
\right),
$$

where:

- \(d(x,x')\) is the distance between the one-dimensional day indices,
- \(\ell\) is the length scale,
- \(p\) is the periodicity.

In the implementation, \(p=365.25\) days is fixed and \(\ell\) is initialized at 40 days and optimized within \([0.1, 100000]\).

The model kernel is

$$
k(x,x')
=
1 \cdot k_{\mathrm{per}}(x,x')
+
k_{\mathrm{white}}(x,x'),
$$

where the multiplicative constant kernel is fixed at 1.0 and the `WhiteKernel` noise level is initialized at 0.1 and optimized within \([10^{-5}, 10]\).

This follows the semantics of scikit-learn's `ExpSineSquared` implementation and its additive kernel composition.

### Posterior prediction

For training inputs \(X\), observations \(y\), and a test input \(x_*\), the standard Gaussian-process posterior mean can be written as

$$
\mu_* = K_*^\top K_y^{-1} y,
$$

and the posterior variance as

$$
\sigma_*^2
=
k(x_*,x_*)
-
K_*^\top K_y^{-1}K_*.
$$

The implementation obtains predictive means and standard deviations from `GaussianProcessRegressor.predict(..., return_std=True)` and constructs nominal 95% Gaussian intervals as

$$
\mu_* \pm 1.96\,\sigma_*.
$$

In addition to the explicit `WhiteKernel`, the regressor is configured with `alpha=10^{-8}`, which supplies a small diagonal term for numerical stabilization.

### Circular wind direction

Wind direction is an angular quantity on a circle, so 359° and 1° are close even though their ordinary arithmetic difference is 358°. The implementation avoids this discontinuity.

For hourly angles \(\phi_1,\ldots,\phi_n\), the daily circular mean is computed as

$$
\theta
=
\operatorname{atan2}
\left(
\frac{1}{n}\sum_{i=1}^{n}\sin\phi_i,
\frac{1}{n}\sum_{i=1}^{n}\cos\phi_i
\right),
$$

then mapped to \([0,360)\) degrees.

The GP does not regress directly on degrees. Instead, it fits two independent scalar GPs:

$$
s(x) = \sin\theta(x),
\qquad
c(x) = \cos\theta(x).
$$

The predicted direction is reconstructed with

$$
\hat{\theta}(x)
=
\operatorname{atan2}
\left(
\hat{s}(x),
\hat{c}(x)
\right)
\pmod{360}.
$$

To estimate angular uncertainty, the implementation applies a first-order delta-method approximation to `atan2`. With predicted sine mean \(\hat{s}\), cosine mean \(\hat{c}\), and independent posterior standard deviations \(\sigma_s\) and \(\sigma_c\),

$$
\operatorname{Var}(\hat{\theta})
\approx
\frac{
\hat{c}^{\,2}\sigma_s^2
+
\hat{s}^{\,2}\sigma_c^2
}{
\left(\hat{s}^{\,2}+\hat{c}^{\,2}\right)^2
}.
$$

The resulting angular standard deviation is converted from radians to degrees.

This uncertainty construction is an approximation because the two fitted GPs are independent; the covariance between the sine and cosine predictions is not modeled.

## Methodology

The complete pipeline follows these stages:

1. Configure a fixed random seed, location, time range, model settings, and output directories.
2. Build an Open-Meteo Historical Weather API request for hourly observations.
3. Download the response, supporting both JSON payloads and CSV responses.
4. Normalize column names and validate the presence of all required hourly variables.
5. Convert timestamps to datetimes and aggregate hourly observations to daily targets.
6. Compute wind direction with a circular mean rather than an arithmetic mean.
7. Interpolate and forward/backward fill missing daily target values, then enforce strict dataset validation.
8. Create a chronological 80/20 train/test split using only `day_index` as the predictor.
9. Fit one GPR per scalar target and two GPs for wind direction.
10. Generate test predictions and posterior standard deviations.
11. Compute target-specific metrics, including circular metrics for wind direction.
12. Fit final models on the full validated daily dataset.
13. Produce dense predictions over 11,000 evenly spaced time points.
14. Compute and save a 7-day persistence baseline for comparison.
15. Generate diagnostic figures and write reproducibility metadata.
16. Write an audit report and build a ZIP submission package.

### Why chronological evaluation matters

The split is not randomized. For \(n\) daily observations and test fraction \(q=0.20\), the split index is

$$
s = \left\lfloor n(1-q)\right\rfloor.
$$

Training uses rows before \(s\), while testing uses rows from \(s\) onward.

This preserves temporal ordering and avoids leakage from randomly mixing future and past observations in a forecasting-style evaluation.

## Model Specification

### Scalar targets

Each non-direction target is passed to `fit_scalar_gp`, which constructs

```text
1.0 * ExpSineSquared(
    length_scale=40.0,
    periodicity=365.25,
    length_scale_bounds=(0.1, 100000.0),
    periodicity_bounds="fixed",
) + WhiteKernel(
    noise_level=0.1,
    noise_level_bounds=(1e-5, 10.0),
)
```

and fits

```text
GaussianProcessRegressor(
    alpha=1e-8,
    normalize_y=True,
    n_restarts_optimizer=10,
    random_state=1,
)
```

during normal execution.

Optimizer restarts are reduced to zero when `ASSIGNMENT_TEST_MODE=1`, making the offline validation path deterministic and less expensive.

### Optimization

`GaussianProcessRegressor` optimizes the non-fixed kernel hyperparameters by maximizing the log-marginal likelihood. In this implementation:

- the periodicity is fixed at 365.25 days;
- the periodic length scale is optimized;
- the white-noise level is optimized;
- the multiplicative constant kernel is fixed at 1.0;
- `random_state=1` is used;
- ten optimizer restarts are used in normal mode.

No external hyperparameter-search framework is used.

## Evaluation

### Linear targets

For scalar targets, the following metrics are written to `outputs/tables/test_metrics.csv`.

Mean absolute error:

$$
\operatorname{MAE}
=
\frac{1}{n}
\sum_{i=1}^{n}
\left|y_i-\hat{y}_i\right|.
$$

Root mean squared error:

$$
\operatorname{RMSE}
=
\sqrt{
\frac{1}{n}
\sum_{i=1}^{n}
\left(y_i-\hat{y}_i\right)^2
}.
$$

The normalized RMSE is implemented as

$$
\operatorname{NRMSE}_{\%}
=
100
\frac{\operatorname{RMSE}}
{\operatorname{SD}(y)},
$$

where the sample standard deviation is computed with `ddof=1`.

The coefficient of determination is the standard scikit-learn \(R^2\) score.

The signed mean error stored as `Mean_Error` is

$$
\frac{1}{n}
\sum_{i=1}^{n}
\left(y_i-\hat{y}_i\right).
$$

### Predictive-interval coverage

For scalar targets, the code constructs the nominal 95% interval

$$
[\hat{y}_i-1.96\sigma_i,\ \hat{y}_i+1.96\sigma_i]
$$

and reports the empirical percentage of test observations contained in that interval.

This is an empirical coverage diagnostic, not a guarantee of exactly 95% frequentist coverage.

### Wind-direction metrics

Angular errors are wrapped to the shortest signed or absolute path around the circle. The absolute circular error is

$$
e_i
=
\left|
\left(
y_i-\hat{y}_i+180
\right)
\bmod 360
-
180
\right|.
$$

Circular MAE and RMSE are then computed from these angular errors. Circular NRMSE is normalized by 180 degrees in the implementation. \(R^2\) is not reported for wind direction.

Wind-direction coverage is evaluated using the angular error and the estimated angular standard deviation:

$$
e_i \leq 1.96\sigma_i.
$$

### Baseline

A 7-day persistence baseline is implemented. For each test day, it uses the observed value from seven days earlier when that historical observation exists. The baseline is evaluated with the same linear or circular error convention used by the corresponding GPR metric.

The final metrics table also reports

$$
100
\frac{\operatorname{RMSE}_{\mathrm{baseline}}
-
\operatorname{RMSE}_{\mathrm{GPR}}}
{\operatorname{RMSE}_{\mathrm{baseline}}},
$$

stored as `RMSE_Improvement_percent`.

## Usage

### Google Colab workflow

The generated notebook uses three cells:

1. Write the complete `assignment_solution.py` implementation.
2. Execute the implementation with `ASSIGNMENT_TEST_MODE=0` and the configured output root.
3. Export the notebook, script, audit report, and generated data/output artifacts into a ZIP package.

The source also contains a standalone `run()` entry point in the embedded implementation. The default runtime output directory is:

```text
assignment_solution_runtime/
```

and can be overridden with:

```bash
export ASSIGNMENT_OUTPUT_ROOT=/path/to/output
```

The script location can be overridden with:

```bash
export ASSIGNMENT_SCRIPT_PATH=/path/to/assignment_solution.py
```

### Offline validation mode

Set

```bash
export ASSIGNMENT_TEST_MODE=1
```

to replace the remote download with a deterministic synthetic hourly fixture generated from `numpy.random.default_rng(SEED)`.

This mode is intended to validate the pipeline mechanics offline. It is not a substitute for the real historical weather data used in the production path.

## Reproducibility

The implementation uses several explicit measures to support reproducibility:

- deterministic seed `SEED = 1`;
- deterministic offline fixture under `ASSIGNMENT_TEST_MODE=1`;
- explicit geographic coordinates and date range;
- explicit units and timezone;
- chronological rather than randomized evaluation;
- explicit dataset-schema validation;
- recorded Python, platform, NumPy, pandas, and scikit-learn versions;
- persistent CSV, JSON, PNG, Markdown, notebook, and ZIP artifacts;
- a generated audit report documenting methodology and known limitations.

The runtime metadata records the data-source string returned by the acquisition function. Because the production path retrieves data from a live historical API, exact byte-for-byte reproducibility also depends on the requested API response remaining available and unchanged.

## Limitations

### Data limitations

The modeled interval spans only 264 days, which is shorter than one annual period. A fixed 365.25-day periodicity is therefore imposed by design, but the dataset does not provide a complete empirical cycle with which to validate annual repetition.

The data source is an Open-Meteo historical weather API backed by model/reanalysis products rather than a single ground station. This is appropriate for a reproducible gridded-data workflow, but it should not be treated as station-observed ground truth.

### Modeling limitations

The predictor space contains only `day_index`. The model does not use lagged weather variables, spatial information, exogenous atmospheric features, calendar embeddings, or autoregressive residual structure.

Each target is modeled independently. Cross-target correlations, such as the relationships among temperature, humidity, pressure, and precipitation, are not represented.

The periodic kernel assumes an exactly repeating structure with a fixed period. This can be restrictive for weather processes whose seasonal phase, amplitude, and dynamics vary over time.

Wind direction is handled as circular data, but its predictive uncertainty is obtained with a first-order delta-method approximation and independent sine/cosine GPs. A probabilistically coherent circular likelihood is not implemented.

The 95% intervals are Gaussian intervals derived from model predictive standard deviations. Their empirical coverage is measured after fitting rather than calibrated with an additional calibration procedure.

### Computational limitations

Exact Gaussian-process inference scales cubically with the number of training observations in the standard implementation. For substantially larger time series, sparse or inducing-point methods would be more appropriate.

The pipeline also fits a separate GP for each of the 22 targets, plus two additional GPs for wind direction, which increases the total training cost.
